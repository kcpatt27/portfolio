Case study - No. 01

Fixture

Release candidate - PrivatePython - FastAPI - FreeCAD - Blender

A local-first harness that turns chat into programmatic CAD operations. The model proposes named tools; the client confirms, executes, and undo-wraps them.

The problem

CAD scripting is powerful but brittle. Letting a model write Python into FreeCAD or Blender makes the failure mode arbitrary code with no contract, no confirmation, and no reliable undo. Fixture keeps the model inside a registered tool catalog: every mutation has a JSON schema, a permission tier, and an undo transaction.

Constraints

  • No model-written code execution. Python actions are stripped.
  • Named tools only; unknown tools and invalid arguments are dropped.
  • Confirm-tier mutations stay pending until Apply.
  • Every mutating runner is undo-wrapped in FreeCAD or Blender.
  • Local by default; the OpenRouter lane is opt-in and sends no document bytes.

Evidence

Gate PASS: 140 pytest, FreeCAD 92/0, Blender 29/0. On a 60-case planner suite, Fixture passed 96.7-98.3% of cases against 57.6-74.6% for the closest open-source assistant, with the failure analysis kept alongside the result. The release tree includes two scripted STEP/STL desk cases: a 4-piece laptop cradle and a 2-piece under-desk shelf. The keyboard design is private and appears only in the demo.

What I own

Architecture, harness, both clients, the tool contract, the benchmark, the release gate, and the scripted desk designs. The project is solo-built; the claim I care about is the invariant: the model proposes, the infrastructure decides.

Limits

Fixture is a release candidate, not a public repo yet. The keyboard CAD files stay private. The benchmark measures the planner turn, not a full multi-turn product comparison. There is no production NURBS/B-Rep or DFM claim here; the geometry work is FreeCAD Part/PartDesign, scripted solids, and STEP/STL.
